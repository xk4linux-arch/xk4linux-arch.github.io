Coupon Logic Bypass

How alternating coupon codes exploits a stateless deduplication check to achieve 100% off on a €666 item - no scripts required, browser only.

Challenge Setup

Intigriti's October 2026 CTF dropped a Halloween-themed candy store. The goal: buy The Midnight Collection (priced at €666.00) using only the €66.00 credit you're given on registration. The flag is in the order receipt.

The store has two coupon codes available:

CodeDiscountRestriction
NIGHT2020% offOne per session
NEWS3030% offFirst order only (via newsletter)

Applying both once gives 50% off: €666.00 → €333.00. Still €267 short of your balance. Even with both, you need to stack them more than once — which the UI explicitly blocks.

Recon: Reading the Stack

Opening DevTools and watching network traffic reveals the architecture:

Browser → AWS ALB → istio-envoy → Python BaseHTTPRequestHandler → Node.js

Cart state is managed in-memory by the Node.js layer. The coupon endpoint is: 

POST /api/cart/coupon
Content-Type: application/json

{"code":"NIGHT20"}

When you try to apply NIGHT20 a second time, the server returns: 

{"error": "Coupon already applied"}

The duplication check lives in the Node.js layer and compares the submitted code against the last applied coupon stored in the session — not against the full list of applied coupons.

The Discovery

This was found by accident during testing, which is often how the best bugs are found.

While experimenting, the following sequence was tried:

  1. Apply NIGHT20 → accepted (count: 1)
  2. Apply NEWS30 → accepted (count: 1)
  3. Apply NIGHT20 again → accepted (count: 2) ???
  4. Apply NEWS30 again → accepted (count: 2) ???

At step 3, NIGHT20 was expected to be rejected ("already applied"). It wasn't. The server accepted it because the last applied code was NEWS30, not NIGHT20. The check only asks "is this code the same as the last one?" — not "is this code anywhere in my applied list?"

Root Cause: Stateless Deduplication

The deduplication logic effectively does this: 

// Node.js coupon handler (reconstructed from behaviour)
function applyCoupon(session, code) {
  if (session.lastCoupon === code) {
    throw new Error("Coupon already applied");
  }
  session.lastCoupon = code;
  session.promotions.push({ code, discount: COUPONS[code] });
  // discounts are additive: NIGHT20×2 + NEWS30×2 = 40% + 60% = 100%
}

Instead of checking session.promotions.some(p => p.code === code), it only checks the last entry. Alternating between two codes resets the lastCoupon pointer each time, bypassing the guard entirely.

The discount model is additive:

StepCode AppliedRunning DiscountPrice
1NIGHT20 ×120%€532.80
2NEWS30 ×150%€333.00
3NIGHT20 ×270%€199.80
4NEWS30 ×2100%€0.00

At €0.00 with €66.00 balance, checkout is unlocked.

The Exploit (Browser Only)

No scripts needed. In the browser console, grab your session cookie, then apply the coupons in alternating order:

  1. Add The Midnight Collection to cart
  2. Subscribe to newsletter to unlock NEWS30
  3. Apply NIGHT20
  4. Apply NEWS30
  5. Apply NIGHT20 again
  6. Apply NEWS30 again
  7. Total is now €0.00 — checkout

Bonus: HTTP Body-Bleed

During deeper analysis, a second attack path was found. The Python BaseHTTPRequestHandler layer acts as a reverse proxy to Node.js but never fully consumes the request body when the path doesn't match any handler (e.g. POST /api/cart — which doesn't exist).

If you craft a request where the body of the outer POST is itself a complete HTTP/1.1 request, Python leaves the bytes in the TCP read buffer. The next read on that connection picks them up and parses them as a new request — bypassing the coupon deduplication entirely because it arrives as a fresh, independent request before Node.js updates lastCoupon. 

# Outer request: POST /api/cart (no handler → body NOT consumed by Python)
POST /api/cart HTTP/1.1
Host: challenge-1026.challenges.intigriti.io
Content-Length: [total_length]

# This IS the body — a complete injected HTTP request
POST /api/cart/coupon HTTP/1.1
Host: challenge-1026.challenges.intigriti.io
Cookie: session=[your_session]
Content-Type: application/json
Content-Length: 20

{"code":"NIGHT20"}

This technique — sometimes called HTTP Body-Bleed or request tunnelling — works because the proxy layer and the application layer have inconsistent body-consumption behaviour. The alternating-code method turned out simpler, but the body-bleed path is the more interesting finding architecturally.

Takeaways

  • Deduplication checks must compare against the full set of applied items, not just the last one
  • Additive discount models need an explicit cap or they become a free money printer
  • Multi-layer proxy stacks (Python → Node.js) can create request-parsing inconsistencies that enable request tunnelling
  • Sometimes the simplest test — "what if I just apply it twice?" — finds what complex tooling misses
